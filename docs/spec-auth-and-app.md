## למה הטלפון מאומת בוואטסאפ

הטלפון מקשר בין האתר לבוט: הזמנות, פניות והנחת הכושר מזוהות לפיו. טלפון
לא מאומת אומר שכל אחד יכול לרשום את המספר של מישהו אחר ולראות בבוט את ההזמנות
שלו, או לקבל הנחה על שמו.

**SMS עולה כסף ודורש ספק (Twilio).** לעומת זאת, כשהמשתמש **שולח** הודעה למספר
העסקי, Meta כבר מאמתת את מספר השולח. אנחנו רק צריכים לקשור את ההודעה למשתמש
באתר, וזה מה שהקוד החד-פעמי עושה.

## זרימת ההרשמה

```text
/signup  שם, אימייל, סיסמה, טלפון
   │  supabase.auth.signUp — השם והטלפון נשמרים ב-metadata
   │  טריגר ב-Postgres יוצר שורה ב-profiles (phone_verified = false)
   ▼
/verify-phone  "שלחו לנו בוואטסאפ את הקוד 482913"
   │  כפתור: wa.me/972554680476?text=קוד אימות: 482913
   │  הבוט מקבל את ההודעה → rpc verify_phone(טלפון השולח, קוד)
   │  הדף בודק כל 3 שניות אם הטלפון אומת
   ▼
/app  היום
```

- **אישור אימייל — כבוי.** הדוא"ל המובנה של Supabase מוגבל בקצב ולא מיועד
  לפרודקשן, והאימות האמיתי כאן הוא הטלפון. **לאמת בתיעוד הרשמי לפני הכיבוי.**
- **משתמש שלא אימת טלפון** מגיע תמיד ל-`/verify-phone`, מכל עמוד באפליקציה.
  החנות פתוחה לכולם.
- **הקוד:** 6 ספרות, תקף 15 דקות, חד-פעמי, ו**רק מהטלפון שנרשם**. קוד שנשלח ממספר
  אחר נדחה.
- **החלפת טלפון בפרופיל** מבטלת את האימות, ודורשת לאמת שוב.
- **ייחודיות:** אותו טלפון לא יכול להיות מאומת אצל שני משתמשים. משתמש שרק *טוען*
  למספר (לא אימת) אינו חוסם את הבעלים האמיתי.

### תנאי אבטחה — חתימת Meta

הבוט מאמת טלפון לפי שדה `from` ב-webhook. היום ה-webhook לא בודק שהבקשה באה
באמת מ-Meta. מי שיודע את הכתובת יכול לשלוח בקשה מזויפת עם כל `from`, ולאמת
בעזרתה מספר שאינו שלו.

**לכן בדיקת החתימה (`X-Hub-Signature-256`, HMAC-SHA256 עם ה-App Secret) היא תנאי
להפעלת האימות.** עד שהיא עובדת, האימות פועל בסביבת בדיקה בלבד.

## נתונים — Supabase Postgres

כל הטבלאות ב-`public`, עם RLS. הפרויקט מוגדר **בלי חשיפה אוטומטית** ל-Data API,
ולכן כל טבלה מקבלת `GRANT` מפורש, רק למה שנדרש.

### `profiles` — שורה לכל משתמש

| עמודה | סוג | הערות |
|---|---|---|
| `id` | uuid, PK | = `auth.users.id` |
| `display_name` | text | |
| `phone` | text | `972501234567`. חובה בהרשמה |
| `phone_verified` | boolean | ברירת מחדל `false`. **המשתמש לא יכול לשנות** |
| `weekly_goal` | int | 3–7, ברירת מחדל 5 |
| `units` | text | `metric` / `imperial` |
| `show_streak` | boolean | ברירת מחדל `true` |
| `timezone` | text | ברירת מחדל `Asia/Jerusalem` |
| `created_at`, `updated_at` | timestamptz | |

- **RLS:** קריאה ועדכון — רק השורה של המשתמש (`id = auth.uid()`). אין insert
  ואין delete מהאתר: השורה נוצרת בטריגר
- **הרשאת עמודות:** `authenticated` מקבל `UPDATE` רק על `display_name`, `phone`,
  `weekly_goal`, `units`, `show_streak`. על `phone_verified` — לא
- **טריגר:** שינוי `phone` מאפס את `phone_verified`
- **ייחודיות:** אינדקס ייחודי חלקי על `phone` כש-`phone_verified = true`

### `activities` — אימון שנשמר

כמו ב-spec-mvp-screens.md: `type`, `started_at`, `ended_at`, `duration_minutes`
(מינימום 1), `distance_km` (null כשאין `pacing`), `calories`, `is_estimated`
(תמיד `true` ב-MVP).

- **RLS:** select / insert / delete רק על שורות של המשתמש. אין update — אימון
  שנשמר לא נערך
- **בדיקות (CHECK):** `type` אחד משישה, משך 1–600 דקות, מרחק וקלוריות אינם שליליים

### `phone_verifications` — קודים חד-פעמיים

`user_id`, `phone`, `code`, `expires_at`, `used_at`.

- **אין גישה מהאתר בכלל.** הקוד נוצר בפונקציה `start_phone_verification()`
  (security definer, מופעלת ע"י המשתמש המחובר, מחזירה את הקוד), ונבדק בפונקציה
  `verify_phone(phone, code)` — **רק ל-service_role**, כלומר רק לבוט

## המסכים

| כתובת | מסך | מחובר? |
|---|---|---|
| `/` | דף תדמית | לא. מחובר → `/app` |
| `/login`, `/signup` | התחברות והרשמה | לא |
| `/verify-phone` | אימות טלפון | כן |
| `/app` | היום | כן + טלפון מאומת |
| `/app/new` | אימון חדש, והאימון החי כשכבה מעליו | כן + טלפון מאומת |
| `/app/progress` | התקדמות | כן + טלפון מאומת |
| `/app/profile` | פרופיל ועריכה. נכנסים מהאווטאר בכותרת | כן + טלפון מאומת |
| `/app/shop` | חנות | פתוח לכולם |

**שומר הכניסה:** `proxy.ts` מרענן את ה-session בכל בקשה (הדרך הרשמית של Supabase
ב-Next.js 16). ההחלטה אם להכניס נעשית **בשרת, בכל עמוד**, עם `getClaims()`.
ה-proxy לבדו אינו מנגנון הרשאה.

## מה נשאר בחוץ

- **הנחת כושר בבוט לפי נתוני אמת:** אפשרי עכשיו, כי יש `activities` וטלפון מאומת.
  סבב נפרד
- **שחזור סיסמה:** Supabase שולח מייל, והדוא"ל המובנה מוגבל. **סבב נפרד**, עם SMTP
- **קישור הרשמה מהבוט** (`/signup?phone=`): מילוי מראש של הטלפון בלבד. האימות
  עדיין בוואטסאפ

## קריטריוני קבלה

1. הרשמה עם אימייל, סיסמה, שם וטלפון מגיעה ל"אימות טלפון".
2. שליחת הקוד לבוט מהטלפון שנרשם מאמתת אותו, והדף עובר ל"היום" לבד.
3. אותו קוד ממספר אחר — נדחה. קוד שפג (15 דקות) או שכבר נוצל — נדחה.
4. משתמש לא יכול לסמן לעצמו `phone_verified` — גם לא בקריאה ישירה ל-Data API.
5. משתמש א' אינו רואה ואינו מוחק אימונים של משתמש ב' (בדיקה שלילית מול ה-API).
6. אי אפשר להגיע ל-`/app` בלי להתחבר, ולא בלי טלפון מאומת.
7. אימון נשמר, מופיע בראש "היום" ומעדכן את הטבעת ואת ההתקדמות.
8. רענון הדף באמצע אימון לא מאבד אותו.
9. כל מרחק, קצב וקלוריות מסומנים "מוערך".
10. שינוי יעד או יחידות בפרופיל משתקף מיד בכל המסכים.
11. `/` מציג דף תדמית למי שלא מחובר, ומעביר מחובר ל-`/app`.
12. webhook בלי חתימה תקפה של Meta נדחה, והאימות לא רץ עליו.
